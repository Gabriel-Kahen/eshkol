# Server-side SSE study and design draft

The first slice serves one loopback HTTP/1.1 client and retains one bounded event frame. The HTTP adapter transfers the accepted connection to an explicit-loop resource lease. The SSE core owns framing, backpressure, and the stream lifecycle. The complete-response API remains available.

## Protocol behavior

The SSE payload for `café\nsecond line` is `data: caf\xc3\xa9\ndata: second line\n\n`. It has 31 UTF-8 bytes. The HTTP chunk is `1f\r\n` followed by the payload and `\r\n`, for 37 bytes on the wire. After the first 14 chunk bytes, the next byte is `a9`, the second byte of `é`. The receiver can dispatch the event once the SSE blank line arrives. A clean HTTP finish separately writes `0\r\n\r\n`. [WHATWG event interpretation](https://html.spec.whatwg.org/multipage/server-sent-events.html#event-stream-interpretation) · [RFC 9112 chunked coding](https://datatracker.ietf.org/doc/html/rfc9112#section-7.1)

| SSE payload | Expected client result |
|---|---|
| `data:\n\n` | One `message` with empty data |
| `event: update\n\n` | No event because the data field is absent |
| `data: one\ndata:\n\n` | One `message` with data `one\n` |
| `data: unfinished\n` followed by EOF | No event because the blank line never arrives |
| `id:\ndata: x\n\n` after an event with an ID | One event with an empty last-event ID |

The isolated C parser at `53220efc1` matched these cases and all 30 two-part splits of the UTF-8 example. A three-part split withheld the blank line until the final feed. A synthetic HTTP decoder recovered the exact 31-byte payload. The existing parser returns an empty type for an explicit empty `event:` field, so the proposed encoder omits empty event-type metadata. Native server and mixed-loop validation are pending. [Existing parser](https://github.com/tsotchke/eshkol/blob/53220efc1638c77d108ab009d4a5e6939c488c7b/lib/agent/c/agent_sse.c#L165-L259)

## Connection lifecycle

At `53220efc1`, the HTTP server stores the accepted socket in its client slot. The ordinary response writes a complete body and closes the socket. Server shutdown also closes any client left in that slot. SSE needs an explicit transfer so the server and stream cannot both retire the same connection. [HTTP accept, respond, and close](https://github.com/tsotchke/eshkol/blob/53220efc1638c77d108ab009d4a5e6939c488c7b/lib/agent/c/agent_http_server.c#L452-L619)

| Transition | Ownership and cleanup |
|---|---|
| Accept → begin | The HTTP server owns the client until lease adoption succeeds. A failed adoption leaves the client slot intact and writes nothing. On success, clear the client slot and transfer the socket to the lease. The HTTP server keeps the listener. |
| Write → would-block → resume | The stream owns the encoded bytes, byte offset, and original deadline. Each nonblocking send takes a short exclusive borrow. The adapter owns the write watch on the caller’s loop while bytes remain pending. |
| Finish → retire | Drain the pending frame and then write the terminal chunk. Retire the stream identity once. Owner-thread cleanup removes its watch, closes the descriptor after the last borrow, and releases the loop retain. |
| Cancel, disconnect, timeout, or scope escape | Stop writing and retire through the same path. An unresolved watch-removal failure retains ownership for recovery through its cleanup ticket. An uncertain descriptor close is recorded and never retried. The scoped wrapper preserves the original exception or continuation escape and rejects re-entry. |

The shared lease reference is #926 at `e102be7e2`. Its blocking wait preserves foreign registrations and filters for its own readiness. A caller-driven write step lets the dispatcher service other ready descriptors while SSE is backpressured. PROCESS retains its budgeted reap protocol and SOCKET retains its cleanup ticket contract. [Shared lease reference](https://github.com/Gabriel-Kahen/eshkol/blob/e102be7e287a137b1986a26f7b3b0561f9b9a360/docs/reference/runtime/resource-leases.md#L71-L119) · [Explicit-loop wait](https://github.com/Gabriel-Kahen/eshkol/blob/e102be7e287a137b1986a26f7b3b0561f9b9a360/lib/core/resource_lease.c#L548-L607)

## Proposed boundary

- **API.** `call-with-http-sse-stream` scopes the accepted connection. `sse-send!` queues an event, `sse-progress!` advances the pending write on the caller’s loop, `sse-finish!` queues clean termination once the frame drains, and `sse-cancel!` requests retirement. Returning from the scope before a clean finish retires the connection without writing further bytes.
- **Framing and bounds.** Use `200 OK`, `Content-Type: text/event-stream`, and chunked HTTP/1.1 framing. Preserve loopback binding and the `network` capability. Validate UTF-8 before admitting the frame. Reject CR, LF, and NUL in metadata. Encode payload line breaks as separate `data` lines. Cap the encoded event chunk at 16 KiB including HTTP chunk overhead. Return `busy` if the slot is occupied and a distinct size error for an oversized event.
- **Deadlines.** Propose one 5-second monotonic budget per pending write, starting on admission and held across retries. Propose a separate 60-second idle timeout between frames. After timeout, cancellation, or disconnect, retire the connection and discard unsent bytes. The producer can observe admission and transport progress. Client dispatch is independently observed by the receiver.

A blocking send-all can hold the caller while the peer stalls. A multi-event queue adds memory and overflow policy. One retained frame bounds memory and gives the producer an explicit backpressure result.

## Acceptance cases for joint review

1. Force the 14-byte short write, then repeated would-block. Verify that the next write starts at byte 14 and that the receiver sees exactly one event with the original contents.
2. Exercise the exact capacity boundary and one byte over. Verify that a second event submitted while a frame is pending cannot change the active bytes or offset.
3. Deliver spurious writable notifications past the original deadline. Verify that no further write occurs. Cover both zero progress and cancellation or peer disconnect after a partial write.
4. Exercise normal return, exception, and continuation escape. Keep PROCESS and SOCKET active on the same loop, cancel SSE after partial progress, and verify that foreign watches continue to work and the SSE descriptor closes once. Inject a watch-removal failure and verify deferred recovery through the cleanup ticket.

Duplicate bytes, a retry that extends the deadline, or disappearance of a foreign watch would disprove the contract.

**Review decisions.** Confirm the published implementation base and the adapter/scaffold owner or branch. Review when the connection transfers, which code tracks the write watch, the watch-removal recovery path, and the proposed framing, limits, and acceptance cases before implementation.
