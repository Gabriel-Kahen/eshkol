## Conclusion

Process launching, pipe capture, exit status, termination, cleanup, the portable
event loop, basic Unix-domain socket clients, SSE transports, and a durable
journal already exist. The principal first-week gap is a coherent public
subprocess stream contract on the shared event loop: incremental reads, lossless
flow control, bounded waits, and explicit resource ownership.

The existing pieces should be extended. Their presence alone does not establish
that the complete agent IPC workflow is implemented or tested across engines.

## Concrete subprocess observations

### Ownership foundation identified during language-design review

The audited revision also contains an implemented common native resource registry
([inc/eshkol/core/handle.h:5](https://github.com/tsotchke/eshkol/blob/51a93586951b1c75b413b14531d0465c660ae579/inc/eshkol/core/handle.h#L5))
and an experimental native `--strict-resources` checker
([docs/development/strict_resource_ownership.md:3](https://github.com/tsotchke/eshkol/blob/51a93586951b1c75b413b14531d0465c660ae579/docs/development/strict_resource_ownership.md#L3)).
These are existing facilities to extend, not future infrastructure to recreate.
The registry admits FILE, SOCKET, and EVENT_LOOP kinds, with exclusive leases and
busy-on-close while borrowed. A process kind and stream contracts require explicit
extensions. The checker currently covers stock network acquisitions and supported
control forms; resource-sensitive loops, continuations, and VM remain outside its
checked fragment. This does not establish static checking for subprocess streams.

During that review, both existing native suites `tests/core/handle_lifecycle_test.cpp`
and `tests/core/handle_c_api_test.c` passed when compiled directly with
`lib/core/runtime_handle.cpp`. This is Linux native registry evidence only.

### Observed agent subprocess behavior

1. **Output retention:** a successful child wrote 17,825,792 stdout bytes and
   three stderr bytes. Waiting, then requesting up to 18 MiB of stdout, returned
   16,777,216 stdout bytes and the three stderr bytes. The native drainer
   explicitly continues reading while dropping bytes after its cap.
2. **Positive deadline:** a child running `sh -c 'sleep 1'` with a 100 ms wait
   returned the timeout status after approximately 1,002 ms. The Linux path
   closes its pipe descriptors and then joins blocking readers, which can wait
   for pipe EOF.
3. **Zero deadline:** waiting with zero on a child running `sleep 0.3` returned
   the exited status after approximately 301 ms. The Linux zero-valued timer is
   disabled before a blocking `waitpid` call. Zero-timeout semantics need to be
   explicit in the design.
4. **Resource lifetime:** process destruction closed the stdout descriptor,
   but the internal stdout-descriptor accessor still returned its old number.
   Descriptor reuse makes it important to reject closed handles before lending
   resources to event-loop callers.

These observations apply to the native Linux agent implementation at this
commit. They do not establish identical behavior on other platforms or engines.

## Socket evidence and API differences

The live Unix-socket driver at [scripts/run_v14_connection_gate.sh:302](https://github.com/tsotchke/eshkol/blob/51a93586951b1c75b413b14531d0465c660ae579/scripts/run_v14_connection_gate.sh#L302) rejects only output lines
beginning with `FAIL`, while the fixture places its result after a test label.
It then requires the T4 label, rather than a successful T4 result. An illustrative
failing T4 line passed those shell predicates during the audit. This demonstrates
an insufficient checker; it is not an observed socket runtime failure.

The builtin and agent FFI socket connectors also have different failure values
(`#f` versus `-1`). Native socket sending uses a C string length, while the VM
path accepts string byte length or a bytevector; receive-size caps differ.
Both builtin receive paths collapse no-data, EOF, and errors to `#f`. The later
socket design needs to choose the intended public surface and define these
outcomes consistently.

## Recommended first slice and design decisions

Keep this week's implementation focused on subprocess streams using the existing
process and event-loop facilities. The design note should settle:

1. Public stdout/stderr stream access and lifetime: owning process versus
   borrowed resource, closed-handle checks, unregister/close ordering.
2. Incremental read outcomes: data, would-block, EOF, and error, with byte lengths.
3. Lossless bounded buffering: how a slow consumer pauses draining without
   silently discarding bytes, and how both output streams continue making progress.
4. Deadline and cancellation behavior: distinguish child exit, wait timeout,
   cancellation, and cleanup; avoid competing readers or process-global timer
   assumptions when the shared loop owns stream progress.
5. Engine/platform boundaries: what JIT and AOT must demonstrate, what the VM
   supports or explicitly rejects, and the Windows adaptation.

Acceptance should include streamed stdout/stderr, output beyond 16 MiB with a
slow consumer, accurate bounded waits, kill/cancel, early close, and cleanup.
The current internal descriptor accessors alone are not sufficient evidence of
a safe public API.

Unix-socket event-loop integration and SSE integration remain subsequent slices.
Durable session persistence is inventoried here; this audit does not assign its
implementation ownership. The one-page design note and implementation PR are
separate deliverables.
